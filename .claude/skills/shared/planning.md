# PRD、项目术语与架构

## PRD 追问

先写草稿，再按 [grilling](../mattpocock/grilling/SKILL.md) 分轮追问：每轮只问前提已定的问题，每题附推荐答案，能查到的事实自己查。代决策按 [开发流程契约](workflow-contract.md)，原文的确认关卡按 [参考库](reference-libraries.md) 覆盖。补充：
- 开场写出一句话核心假设，指出缺口：用户是谁、为什么做、成功标准、硬约束。
- 分辨用户“想要的”和“应该想要的”，用用户的原话复述确认。能预测用户对接下来三个问题的反应时收敛。
- 需求包含多个独立能力时，按 `spec-driven-development` 画能力地图：模块 ID、职责、单向依赖。

以下维度用于查漏，只问相关且未解决的部分：
- 用户、问题、成功标准、核心使用流程；用一个具体场景检查隐含前提。
- 角色与权限、数据来源与输入输出、业务规则、外部系统，只在适用时展开。
- 容易混淆的领域术语，必要时用状态转换说明，例如“删除”是否可以恢复。
- 关键异常和边界：空数据、重复操作、失败恢复、并发、撤销。
- 首期范围、非目标、性能与环境约束。数值必须有来源，不知道就标为待定。
- 优先级、预算与时间、运行维护方式，以及怎样才算可交付。

推荐的阈值记录为“选定的方案”，不能当成已知的业务事实。

## PRD 成文

综合全部讨论、纠正、已有文档、`CONTEXT.md` 和授权后选定的方案，写成最终结论。保留没有被撤销的约束和非目标；不能因为某项要求在最近一轮没有出现就把它漏掉。

结构如下（小项目可以合并章节，不建空章节）：
- **目标与范围**：目的、目标用户、成功标准、首期范围、优先级、非目标。
- **能力地图**：只在有多个独立模块时写，包括模块 ID、职责、依赖链和构建顺序。
- **三级边界**：
  - Always：例如输入校验、统一错误格式、核心逻辑测试；
  - Ask first：例如表结构变更、引入重型依赖、修改全局契约；
  - Never：例如本期范围外的功能、提交明文凭据、放宽测试断言。
- **术语与依据**：链接 `CONTEXT.md`，不复制定义。
- **用户场景与流程**：角色、前置条件、步骤、结果，以及相关的异常分支。
- **功能需求**：每项带稳定标识，写明谁在什么条件下、输入什么、按什么规则处理、产生什么输出或状态变化、异常时怎样，并关联验收。
- **非功能需求**：只写实际适用的指标，带条件、单位和判定方法。
- **验收标准**：关联需求标识，写成可观察的“操作 → 预期结果”，覆盖主流程和关键异常。
- **假设与待决策项**：只在存在时列出，说明影响范围以及是否阻塞。

定稿检查：
- 讨论中的每条有效结论，要么已写进正文，要么明确标为非目标、假设或待决策项。
- 同一术语含义一致，规则和验收一致，权限、状态、异常分支没有歧义。
- 把“快速”“友好”“支持某功能”这类说法改写为具体行为。例如“支持删除”要写清：谁能删、在什么条件下删、数据怎么处理、能否恢复、失败时怎样。
- 读者不回看聊天记录，也能判断验收是否通过。

## 项目术语（CONTEXT.md）

按 [domain-modeling](../mattpocock/domain-modeling/SKILL.md) 维护，格式见其 `CONTEXT-FORMAT.md`。补充：
- 分工：`CONTEXT.md` 只写概念的含义；谁能做、何时做、失败怎么处理写在 PRD；实现和接口写在架构文档。三处互相引用，不重复正文。
- 术语原本写在其他文档里的，迁移到 `CONTEXT.md`，原处改为引用。没有需要定义的术语时，简短说明核对结论，不编造词条。

## 技术栈与接口

- 结合复用调研，用 `source-driven-development` 查官方文档，确定语言与运行时、框架、存储、测试、构建、部署中实际需要的部分，并说明理由和兼容约束。只在确有必要时固定版本，不编造“最新版本”。
- 规划阶段只检查工具是否可用；依赖安装和脚手架生成放到获得授权的实施任务里。
- 定义模块职责、依赖方向、跨模块输入输出、错误语义和数据兼容规则。优先约定跨任务的边界，不提前设计内部函数。
- 有 UI 时，写明用户流程、界面范围，以及加载、空数据、失败等关键状态，并记录 UI Skill 或设计稿的入口；视觉细节交给用户选定的 UI Skill。
