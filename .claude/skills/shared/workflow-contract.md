# 开发流程契约

本套 Skill 共用的衔接规则只写在这里，各入口引用本文件，不另行复制。每个 Skill 都可以单独使用，不要求补做前置阶段。安装时 `shared/` 与各 Skill 目录放在同一级。

## 规则来源

- 优先级：系统与安全约束 > 用户当前明确指令 > 项目 `AGENTS.md`（只在其作用域内生效）> 全局 `AGENTS.md` > Skill 默认做法。Skill 只是工作方法。
- 上下文已加载的规则直接采用；没有加载时读取环境指定的权威路径。规则读取失败时说明缺口，继续不依赖该规则的部分。
- 项目事实、历史决策和对外契约以项目指南指定的来源为准；下面的表格只在项目没有约定时使用。

## 授权与推进

- 用户授权了完整目标时，阶段之间直接交接，不重复请求批准；只请求某一阶段时保持在该范围内。
- 需要用户决定时，先完成已授权的部分，再把真实缺口集中成一轮提问。已有的决定和授权在后续阶段继续有效。
- 验证与改动风险相称：必要检查通过后，只在出现新改动、失败或疑点时补测。

## 需求追问与代决策

- 先读已有输入，写出当前理解，主动找遗漏、隐含前提和矛盾。按 [grilling](../mattpocock/grilling/SKILL.md) 分轮：每轮编号问完前提已定的全部问题，依赖未决答案的留到下一轮。每个问题都附推荐方案和简短理由。具体检查维度见 [规划内容](planning.md)。
- 用户回答“没想过”“你推荐就行”时，直接采用推荐方案并记录理由，不再为同一事项求批。用户授权“剩余都按你的推荐”时，在该范围内一次补齐。
- 代决策必须符合已知目标和首期范围，不扩充功能，也不扩大外部操作权限。凭据和真实业务数据不能编造。
- 文档中区分四类内容：用户明确要求、授权后由 Agent 选定的方案、待验证假设、待决策项。
- 只有回答、调研或实施揭示了新缺口，且现有授权解决不了时才补问，并说明原因。

## 权威来源

| 信息 | 默认位置 | 维护者 |
| --- | --- | --- |
| 项目术语 | `CONTEXT.md`（项目根目录） | project-prd；后续阶段发现新术语时更新此处 |
| 难以逆转的技术决策 | `docs/adr/` | 做出决策的阶段，按 domain-modeling 的 ADR 门槛 |
| 范围、业务规则、验收 | `docs/requirements.md` | project-prd |
| 小项目简报（替代上面两行和架构） | `docs/brief.md` | project-lite |
| 复用调研 | `docs/reuse-research.md` | project-arch |
| 技术栈、模块、接口、UI 设计引用 | `docs/architecture.md` 或其指定的契约文件 | project-arch；实施中确认的变更写回原处 |
| 里程碑与总体顺序 | `docs/implementation-plan.md` | project-plan |
| 单项任务范围、状态、完成证据 | GitHub Issues；未采用时用本地计划或 brief 任务清单 | project-plan / task-implement |
| 仓库约定、文件归属、文档入口、合并策略 | 项目 `AGENTS.md` | repo-init |
| 交付证据 | `docs/delivery.md` | project-delivery |
| 基于代码的架构评审 | `docs/architecture-review.md` | architecture-review |

- 项目已有对应文档时沿用其位置，原地更新，不另建副本。每类信息只在一个地方维护，其他文档链接过去。
- 术语变化时先改 `CONTEXT.md`，再核对受影响的需求、接口、任务和代码命名。已有项目只有旧的 `context.md` 时，首次触及时用 `git mv` 改名并修正链接。
- 采用 Issues 后，本地计划只保留里程碑和链接。接口变化先更新契约，再核对受影响的任务。
- 后续阶段以落盘文档为依据，不依赖没有写下来的聊天内容。

## 参考库

追问、术语、TDD、排错、模块设计、任务拆分、代码评审等通用方法引用第三方原版副本，主源和冲突覆盖规则只写在 [参考库](reference-libraries.md)。

## 阶段衔接

- 新项目：project-prd → project-arch（内部调用 repo-init）→ project-plan → task-implement × N → project-delivery → architecture-review（按需）。小项目：project-lite → task-implement × N。
- 已有项目的增量需求：project-prd 原地更新需求并标注版本 → project-arch 做增量影响分析 → project-plan 拆出带版本号的 Issues。小改动或单点缺陷直接用 task-implement（或全局工具 `leader`，如可用）。
- 换会话时交接：项目路径、任务标识、分支和基线提交、已有产物、已执行的验证、未解决事项。复用已有任务记录，不另建交接日志。
- 并行写代码需要隔离的 worktree、明确的修改边界和集成顺序；换会话不等于代码隔离。

## 模型档位

规划时给每个执行任务标建议档位，供用户选模型以省钱。不写具体模型名。
- **强**：命中任一信号——首个端到端骨架、跨模块接口、并发/事务/数据迁移、鉴权与安全、根因未知的缺陷或性能问题、未定的设计取舍。
- **标准**：其余任务；拿不准时标标准。
- 写法：`建议档位：强|标准 — 理由`，理由指向命中的信号或参照的已有模式。
- 可执行的标准档任务要写到弱模型照做也不偏：参照的已有文件、接口签名、边界用例；待细化的任务细化时再补。
- 执行中不自动升级，换模型由用户决定。

## 完成状态

以下状态分别判断、分别报告，不能互相替代：规划完成、实现完成、集成完成（已进入 main）、验收通过、已提交推送、正式发布。测试通过不等于已合并，构建成功不等于已发布。

## Git 与合并策略

- 产生文件改动的任务，由最外层的 task-closeout 在验证后提交并推送到已确认的目标，阶段切换时不重复确认。用户要求仅本地、不提交或不推送时照做；纯只读评审不做 Git 操作。
- Issue 任务从已核实的远端最新 `main` 开分支，合并方式由项目 `AGENTS.md` 中的 `合并策略` 决定：
  - `auto`（未声明时的默认值）：验收通过、CI 检查（如有）通过后直接合并到远端 `main`，不再等待确认；项目没有自动化测试时降级为 `confirm`；
  - `confirm`：推送任务分支，给出改动摘要、验收证据和合并命令，然后停下等待用户确认，确认后再合并；
  - `pr`：创建指向 `main` 的 PR，按仓库保护规则走检查和审批。
  - 用户本次的明确指令优先于项目配置。
- 升版本、打标签、发布 Release 由 task-closeout 按 `发布策略` 自行决定，不询问：`auto`（默认）在版本进入 main 后执行，`manual` 只建议。
- Issues 增改关闭、部署、包仓库发布需单独授权，规划或评审不算授权。

## 收尾

每个顶层任务结束时，由最外层 Agent 执行一次 [task-closeout](../task-closeout/SKILL.md)，然后再给最终答复。被嵌套调用的 Skill 只把产物和验证记录交回调用方，不自行收尾，避免重复提交或递归调用。收尾不替代验收。某个 Skill 不可用时，完成可行部分并报告缺失的环节。

## 红线

以下行为在任何情况下都不允许：
- 通过删断言、跳过用例或放宽验收来让检查变绿；
- 强推、改写公共历史、绕过 hook 或签名；
- 提交凭据；
- 把没有执行的验证或没有完成的状态说成已完成。
