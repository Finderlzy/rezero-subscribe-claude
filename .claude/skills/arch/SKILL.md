# Arch

通常作为 wayfinder 地图上的一个选型任务来跑。产出：选型 ADR。

范围只到系统形态（单体还是拆分）、技术栈、部署。模块内部怎么切交给 `codebase-design`。

## 1. 摸清用户水平

读 `docs/agents/developer.md`。不存在就按 `grilling` 的格式问一轮，问具体经历，不问自评：

- 写过并上线过的语言和框架
- 自己运维过的东西：数据库、服务器、容器、云服务
- 线上出故障时能自己排查到哪一层
- 这个项目愿意为学新技术花多少时间

答案写进 `docs/agents/developer.md`。之后发现有变化就更新它。

## 2. 实时核实，不靠记忆

每个候选技术都联网查一手来源（官方文档、发布页、源码仓库）：当前稳定版本和发布日期、近一年是否仍在维护、与其他候选是否兼容。每条结论附链接和查询日期；查不到的标“未核实”，不得用记忆补。需要深挖时调用 Skill 工具：`research`。

## 3. 按无聊程度给方案

遵循 Choose Boring Technology：用户没在生产中用过的技术，每用一项花一个**创新额度**。

- **方案一**：零额度。只用用户已会的或最成熟的技术，用户一个人维护得了。
- **方案二**：花一个额度，换一个说得出来的收益。
- **方案三**（可选）：较新的组合。写清要额外学什么、出了事怎么排查。

每个方案列出：组成、花掉的额度、换来什么、日常维护负担。默认推荐方案一，除非需求真的逼出别的。

拿不准的风险点（性能、某个库能不能做到）先调用 Skill 工具：`prototype` 验证，再让用户定。

## 4. 落盘

用户选定后，调用 Skill 工具：`domain-modeling`，把选型写成 ADR，Considered Options 里记下放弃的方案和原因。
