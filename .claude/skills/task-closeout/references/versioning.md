# 版本维护细则

## 版本对象与来源

- 读取版本清单、发布配置、发布记录和项目约定，确定版本的权威来源和**最近发布基线**。基线来自发布记录、标签或发布配置，不是最后一次提交。沿用项目已有的版本策略（统一版本或各包独立版本）。
- 没有版本机制的 Skill 仓库：每个 Skill 在自己的目录下用 `VERSION` 文件独立维护版本，首次发布从 `0.1.0` 开始，用法稳定后发布 `1.0.0`。其他类型的项目沿用现有的清单和发布工具，不额外引入 `VERSION` 文件。
- 先明确公开契约，再判断兼容性。对 Skill，公开契约包括触发条件、必需输入、默认行为、输出和依赖。

## SemVer 判断

| 自基线以来未发布的变化 | 级别 | 示例 |
| --- | --- | --- |
| 不兼容的公开契约变化 | MAJOR | `2.3.1 → 3.0.0` |
| 兼容的新增能力，或把能力标为弃用 | MINOR | `2.3.1 → 2.4.0` |
| 兼容的问题修复 | PATCH | `2.3.1 → 2.3.2` |
| 排版、内部重构、补测试，交付行为没有变化 | 通常不升级 | `2.3.1` |

- 多项变化时取最高级别，不按任务数量累加。
- `0.x` 阶段在没有其他约定时：兼容修复升 PATCH，新增能力或不兼容变化升 MINOR，并说明不兼容之处。
- 预发布标识沿用项目现有规则。

## 执行更新

只在 SKILL.md 规定的条件下实际修改版本：用户要求、准备发布，或项目约定“收尾时更新版本”。

1. 把基线版本按所取级别推进，得到目标版本。
2. **幂等**：当前版本已经覆盖同一批变化时保持不变，不重复升级。
3. 同步必要的关联文件，例如清单、锁文件、文档中写明的当前版本；不全局替换相同的数字，不改写历史发布记录。
4. 缺少基线或兼容性依据时，保留现有版本，并报告缺口和可以确定的影响。已经发布的版本不能覆盖。
5. 需要发布说明时写入 `CHANGELOG.md`，不要把版本记录写进 `AGENTS.md`。

更新版本不等于发布。打标签、创建 Release、部署都需要另外授权。
