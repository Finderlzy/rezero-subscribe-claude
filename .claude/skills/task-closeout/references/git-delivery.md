# Git 提交、推送与合并

## 确认范围

- 检查仓库根目录、当前分支、暂存区和工作区差异、远端、upstream。目标项目可能只是上层仓库的一个子目录。
- 按本次的操作记录确定要提交的文件和改动块，不用 `git add .` 或 `git add -A`。如果分支上有不属于本次的未推送提交，先说明，不要一起推送。
- 同一文件里混有用户自己的改动时，按块暂存或使用隔离的索引；无法可靠分离时保留现状并说明，不清空暂存区。

## 提交

- 根据最终差异写具体的提交信息，需要正文时说明原因和验证情况。多行信息写进临时文件，用 `git commit -F` 提交，之后删除该文件。
- 提交后核对提交号和实际包含的文件。重复收尾不重复提交，不 amend，不 reset。
- hook 失败时修复本次可修复的问题；hook 修改了文件时，复查后再提交。不要绕过 hook 或签名。

## 推送

- 推送目标的优先顺序：用户指定 > 已配置的 upstream > 项目约定。没有明确目标、处于 detached HEAD 或目标有歧义时，保留本地提交并说明。
- 使用明确的 refspec，例如 `git push <remote> HEAD:refs/heads/<branch>`。不推送全部分支或标签，不强推。
- 推送失败时只推这一次，不自动 pull、rebase、merge 后重试。向用户报告仓库路径、提交号、远端与分支、错误原因（去掉凭据）和手动执行的命令。结果不确定时，用只读查询核实远端状态。

## Issue 分支的合并

从 task-implement 收到分支、基线、验收证据、评审结论和目标远端后，先确认验收已通过、独立评审没有未解决的阻塞项、提交范围完整，然后按契约的合并策略处理。

**`auto`（默认）**：通过以下关卡后执行下面的“直接合并”。
- 评审结论缺失或仍有阻塞时不合并，改为推送任务分支并报告原因。
- 项目没有可运行的自动化测试时，降级为 `confirm` 并说明原因。
- 仓库配置了 CI 时，先推送任务分支，用 `gh run list --branch <分支>`、`gh run watch` 或连接器等待本分支触发的检查完成，全部通过才合并；失败时按 task-implement 的排错规则处理。推送没有触发任何检查时记为“CI 未覆盖任务分支”，按本地验证结果继续；无法查询检查状态时降级为 `confirm`。

**`confirm`**
1. 推送任务分支。
2. 向用户给出：改动摘要（`git diff --stat` 加要点）、验收证据、相对最新 main 是否有冲突，以及下面“直接合并”所用的命令。
3. 停下，等待用户确认。用户确认后，按“直接合并”执行。

**`pr`**，或 main 受保护时：
- 推送任务分支，创建或复用指向 main 的 PR，核对实际变更和 Issue 关联。
- 没有 Issue 状态更新授权时，用 `Refs #<编号>` 关联，不用 `Fixes`/`Closes`。
- 不绕过分支保护，不自己批准自己的 PR。需要审批或检查未通过时，报告 PR 链接和待完成的条件。只开启了自动合并或进入合并队列，不能报告为“已合并”。

**直接合并**
1. 重新 fetch main，查看它相对开工基线的变化。如果 main 已经前进，在任务分支或隔离的 worktree 里合入最新 main，按有依据的方式解决冲突，并重跑受影响的检查。冲突涉及无法推断的需求决定时，保留现场并报告。
2. 在干净的集成目录中，以最新的远端 main 为基线合并任务分支，验证合并结果，然后用明确的 refspec 推送到远端 main。
3. 不要重置带有未推送提交的本地 main。

## 核实

- 读取远端 main 和 PR 的实际状态。普通 merge 或 fast-forward 时，确认任务提交已是远端 main 的祖先；squash 或 rebase 合并时，核对 PR 的 merged 状态和实际改动。
- 报告 Issue、分支、PR、提交或合并 SHA，以及远端 main 是否已包含本次改动。
- 分支和 worktree 的清理按项目约定处理。仍承载未交付改动的工作目录要保留。
