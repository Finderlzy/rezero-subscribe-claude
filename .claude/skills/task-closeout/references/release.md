# 标签与 Release 细则

## 前提

- 项目 `AGENTS.md` 的 `发布策略` 为 `auto`（未声明时的默认值），且用户本次没有要求不发布。
- 本次收尾升了版本，或当前版本在仓库中还没有对应标签（上次收尾因未合并而未补打）。
- 版本提交已进入 main：有远端时，用 `git merge-base --is-ancestor <提交> <remote>/main` 核实；没有远端的本地项目以本地 main 为准。远端 main 配置了 CI 时，等该提交的检查通过；失败时不打标签，报告原因。

## 标签

- 命名沿用已有标签（`git tag --list`）的规律。没有先例时：单一版本用 `v<版本>`；各包或各 Skill 独立维护版本时用 `<名称>-v<版本>`。
- 打附注标签，指向 main 上包含该版本号的提交，不打在任务分支的提交上（squash 合并后提交号会变）：`git tag -a <标签> <提交> -m "<名称> <版本>"`。
- 幂等：同名标签已指向同一提交时跳过；指向其他提交时不移动、不删除，报告冲突。
- 用明确的 refspec 推送：`git push <remote> refs/tags/<标签>`，不用 `--tags`。没有远端时只保留本地标签，不创建 Release。

## Release

- 远端是 GitHub，且 `gh` 已登录或有 GitHub 连接器时创建；其他平台有已配置的 CLI 时同理。没有可用工具时报告缺口，不改用网页操作。
- 推送标签会触发项目自己的发布工作流（例如 `.github/workflows` 中监听标签的 workflow）时，不手工重复创建：等它结束，核对它生成的 Release 和其他结果，如实报告。工作流里的部署或包发布属于项目既定流程，Agent 不另外手动执行。
- 同名 Release 已存在时不重建、不覆盖。
- 标题用标签名。说明优先取 `CHANGELOG.md` 中该版本的段落；没有时按上一个标签以来的提交整理“不兼容变化 / 新增 / 修复”，不写内部过程。多行说明写进临时文件，用 `gh release create <标签> --verify-tag --title <标签> --notes-file <文件>` 创建，之后删除该文件。
- 版本带预发布标识（`-alpha`、`-rc` 等）时加 `--prerelease`。不建草稿。只有项目约定了附带产物、且本次已构建并验收时才上传产物。
- 创建后用 `gh release view <标签>` 回读，核对标签、提交和说明。

## 报告

标签名、指向的 SHA、是否已推送；Release 链接，或未创建的原因；触发的发布工作流及其结果。
